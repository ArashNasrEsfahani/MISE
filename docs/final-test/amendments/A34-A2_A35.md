## A34-A2 -- an override for observation-only failures of a world-identical restore (narrow form)

**Plain meaning for Arash:** keep the current check exactly; only when it fails on observation-only discrepancies (what the
detector saw or where the map put it) while the stored kitchen and agent state are exactly identical, let the run go ahead and record the
discrepancy. The check does not establish the cause of the discrepancy (the reset diagnostics point to rendering).

**Rule text.** A14(d) is amended as follows; A14(c)(i)-(v) and every other criterion are unchanged.
1. *Original comparison first.* Each Phase C execution is compared with its Phase A capture under the full registered A14 / A14a / A14b
   comparison, unchanged.
2. *Override.* A failing comparison is overridden (the execution proceeds) if and only if ALL hold: (a) the complete set of breaches is
   confined to the observation-derived kinds `seen_types`, `summary` and `summary.coords`; (b) both captures and both observation
   pipelines are valid (no missing, malformed or non-finite data) and ran with identical frozen settings; (c) the canonical world-only
   snapshots of the two captures are identical at the existing stored precision: every object's identity, type, pose, parents /
   contents, capabilities and all state flags, accessibility, evaluator labels, reference-plan feasibility verdicts, and the agent's
   position, rotation, horizon and standing. Any other discrepancy, or any missing data, stays blocking.
3. *Record.* Each overridden comparison is stored as `obs_drift` (types only in A / only in B, differing summary rows, coordinate deltas).
4. *Calibration (A14(c) restart requirement).* Expressly amended: no recalibration; the existing frozen tau_pos / tau_rot, ceilings and
   pose tolerances are kept unchanged, because the override adds a stricter world condition and widens no tolerance. Summary coordinates
   are not removed from the comparison; they are only excusable under condition (c). Instead, a prospective dev validation runs before
   attempt 2: the 24 dev presentations x 2 fresh captures; PASS iff in 24/24 pairs the comparison either passes or is overridden under
   rule 2, with `obs_drift` counts reported. Fixed before the first capture.
5. *Analysis (disclosed).* The primary analysis keeps every eligible episode, drift or not. Reported in addition, descriptively: `obs_drift`
   counts per arm; SR with drift episodes excluded (labelled descriptive and potentially selection-biased); and, for every arm contrast, SR on
   the common presentation subset with no drift in any compared arm, with its denominators. These cannot establish that drift affected
   arms equally.
6. *Claim.* Two tiers, stated separately: an ordinary pass keeps the registered tolerance-based world checks and the registered
   observation equivalence; an overridden comparison establishes identical stored world snapshots (stricter) but NOT observation
   equivalence. Neither establishes equivalence of planner inputs. It does not prove the absence of reset faults in unmeasured state.

**Why this is narrower than the r1 draft.** It keeps every registered pass; it excuses only failures made solely of observation kinds,
and only when the world snapshots are exactly identical (stricter than the tolerance-based world check). It may still block restores
that are numerically different but practically equivalent; the dev validation shows how often. A narrower type-scoped variant (excuse only
non-task-relevant seen types, e.g. the Stool) would leave the 10 `summary` / `summary.coords` blocked attempts of attempt 1, so it would
not remove the failure class found.

**Why it is fair.** Same rule for all arms; outcome-blind in mechanism (it reads only state comparisons, never plans or success), though
chosen after seeing that attempt 1 failed on observation breaches -- disclosed as such.

**Weakness (stated).** In a drift episode the planner saw a slightly different start picture than the executor; arms may be affected
unequally. The common-subset analysis is how a reader checks this.

**Fingerprint impact.** `sim/final_test/reset_gate.py` (+ selftest) changes and is pinned separately; the decision-rule fingerprint
changes if the acceptance `evidence` root reads `obs_drift` (planned, to report it) -- old / new recorded. Treatment identity unchanged.
